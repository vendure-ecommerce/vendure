In v3 a Role carried both its permissions and the Channels it applied to, and a User held Roles directly. In v4 a Role is only a set of permissions. A `RoleAssignment` grants a Role to a User on one Channel:

```text
v3  role.permissions = [...]
    role.channels    = [channel B]
    user.roles       = [role]

v4  role.permissions = [...]
    role_assignment (user, role, channel B)
```

The same Role can now be granted to different Users on different Channels, so a multi-vendor marketplace no longer needs a copy of each Role per seller.

What else changes with it:

- `User.roles` and `Role.channels` are removed. A new `role_assignment` table replaces the `user_roles_role` and `role_channels_channel` join tables.
- Customers no longer hold a Customer role. A Customer gets the `Authenticated` permission on each Channel they are a member of, and nowhere else.
- Creating, editing and deleting Roles needs the new `CreateRole`, `ReadRole`, `UpdateRole` and `DeleteRole` permissions, bundled in a new `RoleEditor` system Role.
- SuperAdmin is held once and applies on every Channel, including Channels created later.

## Previewing the migration

Run [`previewRoleAssignmentMigration`](/reference/typescript-api/migration/preview-role-assignment-migration) after updating the Vendure packages and **before** migrating, while the database still has its v3 tables. It only reads, so it is safe to run against production:

```ts
import { formatRoleAssignmentMigrationPreview, previewRoleAssignmentMigration } from '@vendure/core';

const queryRunner = dataSource.createQueryRunner();
const preview = await previewRoleAssignmentMigration(queryRunner);
console.log(formatRoleAssignmentMigrationPreview(preview));
await queryRunner.release();
```

<Callout type="warning">
With `synchronize: true`, starting Vendure v4 migrates the data straight away. Run the preview before you start v4 for the first time.
</Callout>

The report has these sections:

- **Migration:** how many Users get rows and how many rows the migration writes, with an estimated run time. The estimate comes from measurements on PostgreSQL. Time the migration on a copy of your production database before you plan the downtime.
- **Administrators and API keys:** no change in access.
- **Customers holding other roles:** Customers who also hold another Role, for example as an Administrator. The migration copies those Roles like any other.
- **Shop customers:** per Channel, how many Customers lose access because they are not a member of it, and how many gain access because they are a member of a Channel the Customer role did not cover. See [Storefront changes](#storefront-changes) for what this means for shoppers.
- **Customer role permissions:** permissions that were added to the Customer role by hand. v4 has no Customer role and no replacement for this, so these are lost.
- **Roles assigned to no channel:** Roles that will have no assignments. Assign them per Channel after migrating if they are still needed.

**Done when:** you have acted on the sections marked "action needed", and noted the "Users with role assignments" and "Role assignments to be written" counts to compare after migrating.

## Migrating the data

In v3 a User received each of their Roles' permissions on every Channel the Role was assigned to. [`migrateRoleAssignmentData`](/reference/typescript-api/migration/migrate-role-assignment-data) writes out that cross product as explicit `(user, role, channel)` rows, with these exceptions:

- **Customer role:** no rows. Customers get `Authenticated` on the Channels they are a member of (the `customer_channels_channel` table), derived at check time.
- **SuperAdmin role:** one row per holder, on the default Channel. That row grants every permission on every Channel.
- **Roles assigned to no Channel:** no rows. These Roles granted nothing in v3, so nobody loses access. The Roles themselves stay.

It also creates the `RoleEditor` Role, without granting it to anyone, and adds the new Role permissions to the SuperAdmin Role.

### Calling the helper

With migrations, call the helper in your v4 migration after the generated statements that create the `role_assignment` table. See [Database migration](/developer-guide/migrating-from-v3/database-migration) for the whole migration.

```ts
import { MigrationInterface, QueryRunner } from 'typeorm';
import { migrateRoleAssignmentData } from '@vendure/core';

export class V4Upgrade1234567890 implements MigrationInterface {
    public async up(queryRunner: QueryRunner): Promise<any> {
        // --- Auto-generated DDL ---
        // (Create role_assignment table and FK constraints)
        // ...

        // --- Populate new table with existing data, verify, archive the old tables ---
        await migrateRoleAssignmentData(queryRunner);
    }

    public async down(queryRunner: QueryRunner): Promise<any> {
        // Auto-generated reverse DDL
    }
}
```

When it succeeds, the helper logs a line like this:

```text
Successfully migrated 1240 role assignments to the role_assignment table in 0.8 s. It now holds 1240 role assignments for 310 users; compare with the counts of previewRoleAssignmentMigration(). The legacy tables were archived as _v3_user_roles_role and _v3_role_channels_channel.
```

**Done when:** the role assignment and user counts in that line match the preview's "Role assignments to be written" and "Users with role assignments".

With `dbConnectionOptions.synchronize` enabled, there is no migration to call it from. Vendure runs it on the first v4 startup instead, in one transaction. Run the preview first all the same.

Table names use the `entityPrefix` of your connection options.

### Startup check

Vendure v4 refuses to start while the `user_roles_role` table still exists with rows. Without this check it would start with an empty `role_assignment` table and lock out every Administrator except the configured superadmin.

### Verification

After copying, the helper checks that `role_assignment` holds exactly the grants the v3 tables describe under the rules above. If any row is missing or extra, it throws an error that names the affected Users, Roles and Channels, and changes nothing else.

## After migrating

### Check the result

1. Log in to the Dashboard as an Administrator who is not a SuperAdmin. They see the Channels they had access to in v3.
2. Run the `roleAssignments` query in the Admin API as a SuperAdmin. It returns the migrated rows.

**Done when:** both checks pass.

### Clear the session cache

Cached sessions keep their v3 permissions until they expire after [`sessionCacheTTL`](/reference/typescript-api/auth/auth-options#sessioncachettl) seconds (300 by default). With the default in-memory cache, restarting Vendure clears them. If your [`SessionCacheStrategy`](/reference/typescript-api/auth/session-cache-strategy) stores sessions outside the process, for example in Redis or through the `DefaultCachePlugin` in the database, clear that store when you switch to v4.

### Grant the RoleEditor Role

In v3 the Administrator permissions covered Role CRUD. In v4 Role CRUD needs `CreateRole`, `UpdateRole` and `DeleteRole`, bundled in the `RoleEditor` Role, which the migration grants to nobody. Until a SuperAdmin grants it, only SuperAdmins can create, edit or delete Roles.

An Administrator can manage a Role only when they hold `RoleEditor` on every Channel where that Role is currently assigned.

### Remove the archived role data later

The migration keeps a copy of the v3 role tables. Once your audit period ends, remove it as described in [Removing the archived role data](#removing-the-archived-role-data).

## Updating your code

### Running the codemod

The `role-assignments` codemod makes the mechanical edits:

```bash
npx vendure codemod role-assignments [path]
```

Without a path it runs in the current directory. It edits:

- GraphQL documents (`.graphql` files and `gql` / `graphql` templates): removes `channels` from Role selections, and `channelIds` from inline `createRole` / `updateRole` inputs.
- TypeORM and Vendure `relations` options: removes `User.roles` and `Role.channels` paths.

Code whose replacement depends on what it is meant to do, such as reading `user.roles`, is left for you. The codemod marks it with a comment naming the replacement and logs each one:

```ts
// TODO(vendure-v4): User.roles was removed in v4. Read the Roles of a User with RoleAssignmentService.resolveUserRoles(ctx, userId); grant or revoke them per Channel with RoleAssignmentService.assign() / remove().
const roles = user.roles;
```

Search for `TODO(vendure-v4)` and work through each comment using the sections below. Running the codemod again adds no duplicate comments. It does not rewrite `RoleChangeEvent` subscribers (see [Events](#events)). For the full list of code it does not change, see [Finding code to update](/developer-guide/migrating-from-v3/breaking-api-changes#finding-code-to-update).

### What stays the same

You do not need to change:

- `@Allow()` decorators and the permissions they name.
- Custom permissions defined with `PermissionDefinition`. SuperAdmins hold them automatically, as before.
- Calls to `RequestContext.userHasPermissions()` and `userHasAllPermissions()` without a `channelId`. They check the active Channel, as before.

### Entities

- `User.roles` and `Role.channels` are removed. Reading either is a compile error, and loading either through `relations` makes TypeORM throw.
  - To read the Roles of a User, use [`RoleAssignmentService.resolveUserRoles(ctx, userId)`](/reference/typescript-api/services/role-assignment-service#resolveuserroles).
  - To find where a Role is granted, query the `RoleAssignment` entity, for example `{ where: { roleId } }`.
  - Queries that join `user_roles_role` or `role_channels_channel` must join `role_assignment` instead.
- `Role` is no longer `ChannelAware`. `ChannelService.assignToChannels()` and `removeFromChannels()` no longer accept a Role.
- The new `RoleAssignment` entity has `userId`, `roleId` and `channelId`.

### Services

To grant or revoke a Role on a Channel, use [`RoleAssignmentService.assign()`](/reference/typescript-api/services/role-assignment-service#assign) and [`remove()`](/reference/typescript-api/services/role-assignment-service#remove). Both check that the active user may grant each Role on its Channel.

```diff
- await this.roleService.assignRoleToChannel(ctx, roleId, channelId);
- user.roles.push(role);
+ await this.roleAssignmentService.assign(ctx, userId, [{ roleId, channelId }]);
```

| v3 | v4 |
|---|---|
| `RoleService.getChannelsForRole()` | Query the `RoleAssignment` entity by `roleId`. |
| `RoleService.assignRoleToChannel()` | `RoleAssignmentService.assign()` |
| `RoleService.getCustomerRole()` | Removed. There is no Customer role. |
| `RoleService.assertActiveUserCanGrantRoles(ctx, roleIds)` | Takes `(roleId, channelId)` pairs. |
| `UserService.createApiKeyUser(ctx, identifier, roles)` | `createApiKeyUser(ctx, identifier)`, then `RoleAssignmentService.assign()`. |
| `ExternalAuthenticationService.createAdministratorAndUser()` | Grants `config.roles` on the active Channel only. In v3 the Roles applied on their own Channels. |

### Events

`RoleChangeEvent` is removed. It was keyed on the Administrator and carried only Role ids, so it could not express the Channel of a grant. Subscribe to [`RoleAssignmentEvent`](/reference/typescript-api/events/event-types#roleassignmentevent) instead:

```diff
- this.eventBus.ofType(RoleChangeEvent).subscribe(event => {
-     const roleIds = event.roleIds;
-     const administrator = event.admin;
+ this.eventBus.ofType(RoleAssignmentEvent).subscribe(event => {
+     const roleIds = event.assignments.map(a => a.roleId);
+     const userId = event.user.id;
      // ...
  });
```

`RoleAssignmentEvent` has `user`, `assignments` (the `{ roleId, channelId }` pairs the write changed) and `type` (`'assigned'` or `'removed'`). It fires in more cases than `RoleChangeEvent` did:

- It is keyed on the User, so it also covers API key Users. To get the Administrator, look it up by `event.user.id`.
- It fires for every write that changes a grant: `assignRolesToUser`, `removeRolesFromUser`, Administrator and API key creation and updates, and SSO Administrator creation. `RoleChangeEvent` fired only on `updateAdministrator` with `roleIds`.
- Deleting an Administrator, an API key or a Channel fires `removed` for the rows it removes.
- A write that changes nothing fires no event.

`AdministratorEvent` still fires as before, but `event.entity.user.roles` is gone with the relation.

### Customers

- `RoleService.getCustomerRole()` is removed. A Customer holds `Authenticated` on each Channel they are a member of, exported as `CUSTOMER_PERMISSIONS` from `@vendure/core`.
- `CUSTOMER_ROLE_CODE` and `CUSTOMER_ROLE_DESCRIPTION` in `@vendure/common` are deprecated.
- If you broadened the Customer role's permissions with a direct repository write, that has no v4 equivalent.

### Sessions and permission checks

- `CachedSessionUser` has a new `globalPermissions` property. It holds the permissions that apply on every Channel, which is how SuperAdmin access is stored. A custom `SessionCacheStrategy` that stores selected fields must include it.
- `RequestContext.userHasPermissions()` and `userHasAllPermissions()` take an optional `channelId`. The default is the active Channel.
- Vendure no longer re-syncs the SuperAdmin Role's stored permissions on startup. Check for `Permission.SuperAdmin` instead of reading the Role's permission list.
- Role assignment changes evict the affected User's cached sessions, so they take effect on the User's next request.

### Admin API

Removed:

- `Role.channels`
- `channelIds` on `CreateRoleInput` and `UpdateRoleInput`

Added:

```graphql
assignRolesToUser(input: { userId: ID!, assignments: [RoleAssignmentInput!]! }): User!
removeRolesFromUser(input: { userId: ID!, assignments: [RoleAssignmentInput!]! }): User!
roleAssignments(options: RoleAssignmentListOptions): RoleAssignmentList!
extend type User { roleAssignments: [RoleAssignment!]! }

input RoleAssignmentInput { roleId: ID!  channelId: ID! }
```

- `assignRolesToUser` adds pairs, and `removeRolesFromUser` removes them. Both skip pairs that need no change.
- The active user must hold every permission of a Role on a Channel to grant or revoke it there.
- `roleAssignments` and `User.roleAssignments` return only the pairs the active user may grant or revoke, so the list can be partial.
- `createAdministrator` and `createApiKey` accept a `roleAssignments` input.

#### `roleIds` now applies to the active Channel only

The `roleIds` input on `createAdministrator`, `updateAdministrator`, `createApiKey` and `updateApiKey`, and the `assignRoleToAdministrator` mutation, still work but are deprecated.

**They now apply to the active Channel only**, the one in the `vendure-token` header. In v3 `roleIds` replaced an Administrator's Roles everywhere, and the Channels came from each Role. Single-channel stores see no difference. Multi-channel clients should move to `assignRolesToUser` and `removeRolesFromUser`, which take the id of the Administrator's User (`administrator.user.id`):

```diff
- updateAdministrator(input: { id: "1", roleIds: ["2", "3"] }) { id }
+ assignRolesToUser(input: {
+     userId: "7"
+     assignments: [{ roleId: "2", channelId: "1" }, { roleId: "3", channelId: "1" }]
+ }) { id }
```

Other changes to these inputs:

- `CreateAdministratorInput.roleIds` is now optional.
- Passing both `roleIds` and `roleAssignments` to a create mutation is an error.
- On update, `roleIds` fails as a whole if it would revoke a pair the active user may not revoke.

#### Administrators and Channels

If you are upgrading from 3.7.3 or later, these already apply:

- An actor can see, update or delete an Administrator only when the actor may grant every Role assignment that Administrator holds. For other Administrators the API returns a not-found error. Only SuperAdmins can see a SuperAdmin.
- `updateChannel` and `deleteChannel` check `UpdateChannel` / `DeleteChannel` on the target Channel, not the active one.

### Testing

- Delete the cached e2e data in `e2e/__data__` after upgrading. The cached database still has the v3 tables, and v4 refuses to start on it instead of migrating.
- `SimpleGraphQLClient.asUserWithCredentials()` switches the client to a Channel token when the login returns exactly one Channel. Customers now get only the Channels they are a member of, so this happens more often. Set the token you want again after logging in.

## Storefront changes

Single-channel storefronts are not affected.

### Customers can use only their member Channels

In v3 the Customer role was assigned to every Channel, so a Customer of Channel A could use customer-scoped operations, such as `activeCustomer`, on Channel B. In v4 a Customer holds `Authenticated` only on the Channels they are a member of.

With the default `CustomerChannelAssignmentStrategy`, nothing changes for the shopper: a signed-in Customer becomes a member of a Channel on their first request there, and that first request already succeeds.

With a [`CustomerChannelAssignmentStrategy`](/reference/typescript-api/auth/customer-channel-assignment-strategy) that declines the assignment, customer-scoped operations on that Channel now fail:

- The error is a thrown `ForbiddenError` (GraphQL error code `FORBIDDEN`), not an `ErrorResult`.
- Public operations on the Channel, such as product queries, still work for the same session.
- The default Channel is never gated. Every signed-in Customer keeps `Authenticated` there.

In v3, a declining strategy only meant the membership was not saved, and the request went through. If Customers should keep access to such a Channel, add the memberships before migrating. The [preview](#previewing-the-migration) lists, per Channel, how many Customers lose access.

### `CurrentUser.channels` lists member Channels only

The `channels` returned by `login`, `authenticate` and `me` used to list every Channel of the instance for a Customer. In v4 it lists the Channels the Customer is a member of, and grows as they visit new Channels. Storefront code that builds a Channel picker from this list, or treats a single entry as a special case, sees fewer entries.

## The archived role data

Once the verification passes, the helper **archives the v3 tables instead of dropping them**. It renames them to `_v3_user_roles_role` and `_v3_role_channels_channel` and removes their foreign keys. It keeps the Customer role row, so the archived rows can still be matched to it.

The archive is a frozen copy of the v3 grants for auditing. It is not a way back to v3: Vendure v4 never reads it, and rolling back means restoring the backup taken before the migration.

<Callout type="warning">
The archive has no foreign keys, so hard-deleting a User does not remove its rows from it. If you erase personal data on request (for example under the GDPR), include the archive in your erasure process until you remove it.
</Callout>

### Removing the archived role data

Once your audit period ends, call [`removeLegacyRoleData`](/reference/typescript-api/migration/remove-legacy-role-data) from a later migration. It drops both archive tables and deletes the Customer role.

```ts
import { MigrationInterface, QueryRunner } from 'typeorm';
import { removeLegacyRoleData } from '@vendure/core';

export class RemoveLegacyRoleData1234567890 implements MigrationInterface {
    public async up(queryRunner: QueryRunner): Promise<any> {
        await removeLegacyRoleData(queryRunner);
    }

    public async down(queryRunner: QueryRunner): Promise<any> {
        // The archive cannot be restored
    }
}
```

It throws, and changes nothing, in two cases:

- `migrateRoleAssignmentData` has not archived the v3 tables yet.
- `role_assignment` holds rows of the Customer role. Until the helper deletes the Customer role, Administrators can still grant it, and deleting it would remove those rows without a `RoleAssignmentEvent` or a session cache eviction. Remove them with the `removeRolesFromUser` mutation first.
