This guide covers what you need to do when upgrading an existing Vendure project from v3.7 to v3.8. Follow the general steps in [Updating Vendure](/developer-guide/updating/) to bump your package versions, then work through the checklist below.

## Checklist

Every project:

- [ ] **Back up your database**, then generate and run a [database migration](#database-migration).
- [ ] Decide whether you need the [order line promotion data migration](#order-line-promotion-data-migration) (you do if any order has a partially cancelled line).
- [ ] Update any of your own dependencies on `@nestjs/*` or `@apollo/server` to [NestJS 12 and Apollo Server 5](#nestjs-12-and-apollo-server-5).
- [ ] Tell your administrators they will need to [log in again once](#admin-api-sessions-are-bound-to-the-admin-api) after the upgrade.

Check these if they apply to you:

- [ ] Storefronts: handle the new [checkout refusal for ineligible shipping methods](#checkout-recalculates-prices-and-re-checks-shipping-eligibility).
- [ ] API clients that send empty strings for required fields: see [blank-string rejection](#blank-strings-are-rejected-for-required-fields).
- [ ] Plugins that read `ctx.session.token` in job queue workers: see [session token on workers](#requestcontextsessiontoken-is-optional).
- [ ] Custom resolvers or event handlers for Product, ProductVariant or Collection updates: see [partial updates from the Dashboard](#the-dashboard-sends-only-changed-fields-for-some-updates).
- [ ] Custom authentication strategies and SSO flows: see [session API binding](#admin-api-sessions-are-bound-to-the-admin-api).
- [ ] Review the [smaller changes](#other-changes) at the end of this page.

## Database migration

**Who is affected:** every project.

v3.8 contains schema changes. They are all non-destructive, but you must generate and run a migration before starting the server against an existing database.

:::warning
Make a backup of your database before running the migration. The new unique constraints on translation tables (see below) remove duplicate rows as part of the migration.
:::

The changes are:

- **New table:** `seller_translation` (Sellers now support localized custom fields).
- **New columns:**
  - `order.pricingUpdatedAt`
  - `refund.destination`
  - `asset.usage` (defaults to `LIBRARY`, so existing assets are unaffected)
  - `administrator.avatarId`
  - `api_key.apiType`
  - `session.apiType` (used by authenticated sessions)
  - Columns for any custom fields you define on `Role`, which now supports custom fields
- **New indexes:** on the `discriminator` column of `history_entry`, `region` and `stock_movement`, the `type` column of `session`, and `search_index_item.productId`.
- **New unique constraints:** a `(languageCode, baseId)` unique constraint on **every translation table**, including translation tables defined by your own plugins.
- **MCP plugin tables:** only if you add the new MCP plugin to your config.

### Duplicate translations

Earlier versions could, under concurrent updates, store two translations of the same entity in the same language. The new unique constraint cannot be added while such duplicates exist.

When you generate the migration with `npx vendure migrate` or [`generateMigration`](/reference/typescript-api/migration/generate-migration/), Vendure detects which translation tables gain the constraint and inserts a [`deduplicateTranslations`](/reference/typescript-api/migration/deduplicate-translations/) call at the top of `up()`. It keeps the most recently updated row for each `(baseId, languageCode)` pair and deletes the others. You don't need to do anything extra.

If you write migrations by hand, or move the constraint DDL into a separate migration file, call it yourself before the constraints are added:

```ts title="src/migrations/1234567890-v38.ts"
import { MigrationInterface, QueryRunner } from 'typeorm';
import { deduplicateTranslations } from '@vendure/core';

export class V381234567890 implements MigrationInterface {
    public async up(queryRunner: QueryRunner): Promise<any> {
        await deduplicateTranslations(queryRunner, [ // [!code highlight]
            'product_translation',
            'product_variant_translation',
            // ...every translation table which gains the constraint,
            // including those of your own plugins
        ]);
        // ...the ALTER TABLE / CREATE UNIQUE INDEX statements follow
    }

    public async down(queryRunner: QueryRunner): Promise<any> {
        // ...
    }
}
```

**What to do:** back up the database, then follow the [Migrations guide](/developer-guide/migrations/) to generate, review and run the migration. Test it against a copy of production data first.

## Order line promotion data migration

**Who is affected:** projects with orders that have **partially cancelled order lines** created before v3.8 (for example, cancelling 1 of 3 units of a line with the `cancelOrder` mutation).

v3.8 fixes how promotion discounts on an `OrderLine` are prorated when its quantity changes. Before v3.8, a partial cancellation reduced the line's `quantity` without rescaling its stored `PROMOTION` adjustments. The corrected calculation reads those stale rows with the wrong basis, which would **inflate the discount** shown on those lines.

The [`rescaleOrderLinePromotionAdjustments`](/reference/typescript-api/migration/rescale-order-line-promotion-adjustments/) helper rewrites the affected rows. Unlike `deduplicateTranslations`, it is **not** added to generated migrations automatically.

**What to do:** add it to the `up()` method of your v3.8 migration (or a migration of its own). It needs no schema change, so it can run at any point in the migration:

```ts title="src/migrations/1234567890-rescale-order-line-promotions.ts"
import { MigrationInterface, QueryRunner } from 'typeorm';
import { rescaleOrderLinePromotionAdjustments } from '@vendure/core';

export class RescaleOrderLinePromotionAdjustments1234567890 implements MigrationInterface {
    public async up(queryRunner: QueryRunner): Promise<any> {
        await rescaleOrderLinePromotionAdjustments(queryRunner);
    }

    public async down(queryRunner: QueryRunner): Promise<any> {
        // This is a one-way data migration - the pre-migration amounts are not recoverable.
    }
}
```

It only touches lines whose quantity was reduced by a cancellation after their adjustments were last calculated, and it logs how many rows it rescaled. If you have no partially cancelled lines, it is a no-op, so it's safe to include when in doubt.

:::note
If an order modification and a cancellation on the same order were stored with the same timestamp, the helper cannot tell which came first. It throws before writing anything and lists the affected OrderLine IDs. Inspect them and pass the correct basis for each via the `ambiguousOrderLineQuantityBases` option. See the [reference docs](/reference/typescript-api/migration/rescale-order-line-promotion-adjustments/) for details.
:::

## NestJS 12 and Apollo Server 5

**Who is affected:** projects or plugins that depend directly on NestJS or Apollo packages, use the GraphQL Playground, or use the Harden plugin.

Vendure v3.8 upgrades to **NestJS 12**, **@nestjs/graphql 14** and **Apollo Server 5**.

**What to do:**

- Update any direct dependencies in your project and plugins to match `@vendure/core`:

  ```json title="package.json"
  {
      "dependencies": {
          "@nestjs/common": "^12.0.1",
          "@nestjs/core": "^12.0.1",
          "@nestjs/graphql": "~14.0.0",
          "@apollo/server": "^5.5.1"
      }
  }
  ```

  Mismatched versions lead to duplicate copies of NestJS in `node_modules`, which usually shows up as dependency injection errors at bootstrap.
- If you use `@vendure/harden-plugin`, its `@apollo/server` peer dependency is now `^5.0.0`.
- If you pass custom Apollo Server plugins via `apiOptions.apolloServerPlugins`, check them against Apollo's [Migrating from Apollo Server 4](https://www.apollographql.com/docs/apollo-server/migration) guide.
- **GraphQL Playground is gone.** Apollo Server 5 removed it. Setting `apiOptions.adminApiPlayground` or `apiOptions.shopApiPlayground` to a truthy value now serves **GraphiQL** at the API path instead. The object form of these options (Playground settings) is accepted but ignored; only its truthiness counts.
- **`adminApiDebug` and `shopApiDebug` are deprecated** and have no effect. You can remove them from your config.

The supported Node.js versions are unchanged: `^20.19.0 || >=22.12.0`. See [Installation](/getting-started/installation/) for the full requirements.

## Admin API sessions are bound to the Admin API

**Who is affected:** every project with administrators, and especially projects with custom authentication strategies or code that creates sessions itself.

Since v3.8, every session records the API it was created for (the new `apiType` column), and the Admin API only accepts sessions created for the Admin API. This closes a hole where a session created on the Shop API for a User who is also an administrator could be used against the Admin API.

**What to do:**

- **Expect administrators to be logged out once.** Sessions created before the upgrade have no `apiType` and are refused on the Admin API, so administrators need to log in again. API keys created before the upgrade keep working.
- Keep authentication strategies that can resolve administrators on `authOptions.adminAuthenticationStrategy` only.
- If you create sessions yourself, for example in a REST controller that completes an SSO callback, pass `'admin'` as the `apiType` argument of `AuthService.authenticate()` or `SessionService.createNewAuthenticatedSession()`. A REST route's context has an `apiType` of `custom`, and sessions created from contexts with no request (scripts, job queue workers) record the Shop API.
- REST routes added by plugins are not checked. If you have one gated by an admin permission, check `ctx.session?.apiType === 'admin'` in the handler.

See the [Auth guide](/core-concepts/auth/#configuring-multiple-authentication-strategies) for the full rules.

## Checkout recalculates prices and re-checks shipping eligibility

**Who is affected:** all storefronts, and projects with time-sensitive prices, promotions or shipping eligibility checkers.

The default order process now recalculates the order when it transitions to `ArrangingPayment`:

1. Prices, promotions, taxes and shipping promotions are recalculated, **without** changing the selected shipping method.
2. If the order has a shipping method that is no longer eligible (for example, a `ShippingEligibilityChecker` with a minimum order value that the recalculated total no longer meets), the transition is refused with the message `cannot-transition-to-payment-with-ineligible-shipping-method`.
3. If all checks pass, a full recalculation runs, including the shipping rate.

So the totals at checkout may differ from what the customer last saw if prices or promotions changed in the meantime.

**What to do:**

- In your storefront, handle an `OrderStateTransitionError` from `transitionOrderToState(state: "ArrangingPayment")` whose `transitionError` says the shipping method is no longer eligible. Re-query `eligibleShippingMethods`, let the customer pick again, then retry.
- Re-read the order totals after the transition rather than relying on values cached from the cart page.

The recalculation itself cannot be turned off. The ineligible-shipping check is controlled by the `arrangingPaymentRequiresShipping` option of [`configureDefaultOrderProcess`](/reference/typescript-api/orders/order-process/#configuredefaultorderprocess), but setting it to `false` also removes the check that an order has a shipping method at all:

```ts title="src/vendure-config.ts"
import { configureDefaultOrderProcess, VendureConfig } from '@vendure/core';

export const config: VendureConfig = {
    orderOptions: {
        process: [
            configureDefaultOrderProcess({
                // Disables both the "has a shipping method" and the
                // "shipping method is still eligible" checks.
                arrangingPaymentRequiresShipping: false,
            }),
        ],
    },
};
```

See [Configuring the default order process](/core-concepts/orders/#configuring-the-default-order-process).

## Blank strings are rejected for required fields

**Who is affected:** API clients and integrations that send `""` or whitespace-only strings for required fields in mutations.

A new input validation step rejects empty or whitespace-only strings for business-required fields on top-level mutation inputs, such as a product name, a facet code or a channel token. These requests now fail with a `UserInputError` (`field-cannot-be-blank`) instead of saving a blank value. Description fields and fields that Vendure fills in itself are not checked.

**What to do:** fix the clients so they send real values. If you can't update them in time, turn the check off:

```ts title="src/vendure-config.ts"
export const config: VendureConfig = {
    apiOptions: {
        inputValidation: {
            requiredFieldValidation: false,
        },
    },
};
```

See [`ApiOptions`](/reference/typescript-api/configuration/api-options/).

## `RequestContext.session.token` is optional

**Who is affected:** plugins that read `ctx.session.token` (or `ctx.req`) in code that runs on the job queue worker.

As part of a security fix ([GHSA-32jm-mf7r-7qw5](https://github.com/vendurehq/vendure/security/advisories/GHSA-32jm-mf7r-7qw5)), serialized `RequestContext` objects no longer contain the session token or the raw request, because serialized contexts are persisted in job data. `RequestContext.session` is now typed as `CachedSession | DeserializedCachedSession`, so `ctx.session.token` is `string | undefined`, and it is always `undefined` on a worker.

**What to do:** fix any TypeScript errors this causes. If a job needs a credential to call another system, pass it in the job payload or, better, use a service-level credential. See [Passing the RequestContext](/developer-guide/worker-job-queue/#passing-the-requestcontext) in the worker guide.

## The Dashboard sends only changed fields for some updates

**Who is affected:** projects with custom resolvers, interceptors or event handlers that assume the `updateProduct`, `updateProductVariant(s)` or `updateCollection` mutations receive the complete input.

The Product, ProductVariant and Collection detail pages in the Dashboard now send only the top-level input fields that were changed, plus `id` and any non-nullable fields. For example, changing a product's name sends `translations`, but no longer sends `facetValueIds`, `assetIds` or `customFields`. Other detail pages still send the full input.

**What to do:** if your code reads fields from the update input, for example via the `input` of a `ProductEvent` or `CollectionEvent`, treat missing fields as "unchanged" rather than "cleared". Load the entity if you need its current state.

## Other changes

- **New Channels get the default roles.** `ChannelService.create()` now assigns the new Channel to the SuperAdmin and Customer roles. If your code did this itself after creating a Channel, you can remove it.
- **New `orderRecalculationStrategy` option.** `orderOptions.orderRecalculationStrategy` controls whether an active order is recalculated when it's read. The default, `NoOrderRecalculationStrategy`, keeps the previous behaviour. Use [`TtlOrderRecalculationStrategy`](/reference/typescript-api/orders/order-recalculation-strategy/) to keep long-lived carts in sync with price and promotion changes.
- **List queries no longer load `channels` implicitly.** `ListQueryBuilder.build()` with a `channelId` used to add the `channels` relation to the query. It now filters by channel without loading it. If your plugin reads `entity.channels` from list results, add `channels` to the `relations` option.
- **Telemetry plugin.** `@vendure/telemetry-plugin` now uses OpenTelemetry `0.223.x` / `2.12.x`. If you installed OpenTelemetry exporters or SDK packages yourself, update them to the same versions. These instrumentations emit only the stable semantic conventions, so HTTP and database span attributes are renamed (for example, `http.method` and `db.statement` no longer exist). Update any dashboards and alerts that query the old names. See [Upgrading from earlier versions](/how-to/telemetry/#upgrading-from-earlier-versions) in the telemetry guide for the full list.
- **Dashboard extensions.** The Dashboard moved to v2 of the Vendure design system (`@vendure-io/ui`). Rebuild your Dashboard extensions and check them visually.
- **Deprecations:**
  - `apiOptions.adminApiDebug` and `apiOptions.shopApiDebug` (no effect, see above).
  - The top-level `widgets` option of `defineDashboardExtension()`. Use `insights.widgets` instead; the old option still works for now.
